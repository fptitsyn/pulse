# Pulse: API для мониторинга доступности сервисов

**Pulse** — серверное приложение для мониторинга доступности веб-сайтов и HTTP API. Проект разработан на **ASP.NET Core Minimal API и PostgreSQL** и позволяет периодически проверять заданные HTTP-эндпоинты, сохранять результаты запросов и определять текущее состояние сервисов.

Это личный проект, направленный на изучение и практическое применение принципов backend-разработки: проектирования REST API, фоновой обработки задач, работы с базами данных, обеспечения безопасности и автоматизированного тестирования.

## Возможности

- **Управление сервисами** — создание, просмотр, редактирование и удаление отслеживаемых сервисов через REST API.
- **Настраиваемые мониторы** — возможность добавить к сервису несколько мониторов с собственными путями, HTTP-методами (GET или HEAD) и интервалами проверки.
- **Фоновый мониторинг** — автоматическое выполнение проверок по расписанию с помощью ASP.NET Core Hosted Service.
- **История проверок** — сохранение времени проверки, HTTP-статуса, длительности запроса и его результата в PostgreSQL.
- **Агрегация состояния сервисов** — вычисление статуса (`Up`, `Down`, `Unknown`) на основе последних результатов активных мониторов.
- **Аутентификация и авторизация** — защита пользовательских данных с помощью ASP.NET Core Identity и bearer-токенов.
- **Защита от SSRF** — использование Microsoft AntiSSRF для ограничения доступа к небезопасным сетевым адресам.
- **Документация API** — интерактивное описание эндпоинтов через Swagger UI в среде разработки.
- **Автоматизированное тестирование** — модульные и интеграционные тесты логики мониторинга, REST API и работы с базой данных.

## Архитектура

В Pulse разделены обязанности управления сервисами, выполнения HTTP-запросов, сохранения результатов и вычисления состояния сервисов.

```text
                         REST API
                            |
                      Авторизация
                            |
                   Управление сервисами
                      и мониторами
                            |
                        PostgreSQL
                            ^
                            |
                     MonitorWorker
                            |
              +-------------+-------------+
              |                           |
       DueMonitorProcessor         ServiceStatusHandler
              |
       +------+------+
       |             |
HttpMonitorChecker  CheckResultWriter
       |             |
  HTTP-сервисы    PostgreSQL
```

### Процесс мониторинга

1. Пользователь регистрируется и создаёт сервис с одним или несколькими мониторами.
2. `MonitorWorker` периодически запускает очередной цикл мониторинга.
3. `DueMonitorProcessor` выбирает активные мониторы, для которых наступило время проверки.
4. `HttpMonitorChecker` выполняет HTTP-запрос и измеряет его длительность.
5. `CheckResultWriter` сохраняет результат, а процессор назначает время следующей проверки.
6. `ServiceStatusHandler` анализирует последние результаты активных мониторов и обновляет состояние сервиса.

### Результаты проверок

Каждая проверка завершается одним из четырёх результатов:

| Результат | Описание |
|---|---|
| `Success` | Сервер вернул успешный HTTP-ответ. |
| `HttpError` | Сервер вернул HTTP-статус, не соответствующий успешному ответу. |
| `Timeout` | Превышено допустимое время ожидания ответа. |
| `NetworkError` | Сетевая ошибка или невозможность установить соединение. |

Общий статус сервиса определяется по последнему результату каждого активного монитора. Сервис получает статус `Up`, если все активные мониторы успешны; `Down`, если обнаружена ошибка и все активные мониторы уже проверялись; `Unknown`, если активных мониторов нет или хотя бы один ещё не проверялся.

## REST API

Операции с сервисами, мониторами и результатами проверок доступны только аутентифицированным пользователям.

| Метод | Эндпоинт | Назначение |
|---|---|---|
| `POST` | `/register` | Регистрация пользователя |
| `POST` | `/login` | Аутентификация и получение токена |
| `GET`, `POST` | `/services` | Получение списка и создание сервисов |
| `GET`, `PUT`, `DELETE` | `/services/{serviceId}` | Управление отдельным сервисом |
| `GET`, `POST` | `/services/{serviceId}/monitors` | Получение списка и создание мониторов |
| `GET`, `PUT`, `DELETE` | `/services/{serviceId}/monitors/{monitorId}` | Управление отдельным монитором |
| `GET` | `/check-results/` | Получение результатов проверок пользователя |
| `GET` | `/services/{serviceId}/monitors/{monitorId}/check-results/` | История проверок монитора |
| `GET`, `DELETE` | `/services/{serviceId}/monitors/{monitorId}/check-results/{checkResultId}` | Просмотр или удаление результата |

Пользователь имеет доступ только к принадлежащим ему сервисам, мониторам и результатам проверок. Новые результаты создаются фоновым процессом мониторинга, а не через публичный POST-эндпоинт.

## Установка и запуск

### Необходимые инструменты

- .NET 10 SDK
- PostgreSQL
- Git
- `dotnet-ef` для выполнения миграций
- Docker для интеграционных тестов с Testcontainers

### 1. Клонирование репозитория

```bash
git clone https://github.com/fptitsyn/pulse.git
cd pulse
dotnet restore
```

### 2. Настройка PostgreSQL

Создайте базу данных PostgreSQL и настройте строку подключения `ConnStr`.

Например, в Linux:

```bash
export ConnectionStrings__ConnStr="Host=localhost;Port=5432;Database=pulse;Username=YOUR_USER;Password=YOUR_PASSWORD"
```

Замените значения на свои учётные данные. У пользователя PostgreSQL должны быть права, необходимые для применения миграций.

### 3. Применение миграций

```bash
dotnet ef database update --project app --startup-project app
```

### 4. Запуск приложения

```bash
dotnet run --project app
```

Адрес запущенного API отображается в консоли.

При запуске в окружении Development интерактивная документация Swagger UI доступна по адресу:

```text
<адрес-приложения>/swagger
```

Для работы с API необходимо зарегистрироваться, получить bearer-токен и передавать его в запросах к защищённым эндпоинтам.

## Тестирование

В проекте используются несколько уровней автоматизированного тестирования:

- **Модульные тесты** — проверка HTTP-запросов, обработки таймаутов, сетевых ошибок и валидации без реальных сетевых соединений.
- **Интеграционные тесты** — проверка API, аутентификации, сохранения данных и выполнения мониторинга на настоящей PostgreSQL.
- **Testcontainers** — запуск изолированных контейнеров PostgreSQL для тестирования.
- **WebApplicationFactory** — запуск ASP.NET Core приложения в тестовом окружении.

Для запуска всех тестов:

```bash
dotnet test
```

Перед запуском интеграционных тестов необходимо убедиться, что Docker работает.

## Статус разработки

Pulse — **развивающийся личный проект**, ориентированный на backend-разработку.

На текущем этапе реализованы аутентификация пользователей, управление сервисами и мониторами, автоматическая проверка HTTP-эндпоинтов, хранение истории проверок и вычисление состояния сервисов.

Пользовательский веб-интерфейс, система уведомлений и расширенная аналитика доступности пока не входят в реализованную функциональность.

## Цель проекта

Я создал Pulse, чтобы получить практический опыт разработки серверного приложения, выходящего за рамки стандартных CRUD-операций.

В процессе работы над проектом я изучаю и применяю планирование фоновых задач, внедрение зависимостей, жизненные циклы сервисов, взаимодействие с базой данных, обработку ошибок HTTP-запросов, защиту исходящих соединений и интеграционное тестирование с использованием реальной инфраструктуры.
